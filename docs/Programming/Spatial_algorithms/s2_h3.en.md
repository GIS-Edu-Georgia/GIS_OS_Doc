# 🌐 Global grids: S2 and H3

On the [grids page](grids_hex.md) we saw how a 2D cell is turned into a single number. Now the same idea **for the whole Earth**: a **discrete global grid system** (DGGS) gives every point a single **cell ID**, and spatial questions (nearby points, falling within a region, aggregation) become **operations on integers**. At that point an entirely ordinary database or a sorted list is enough, and we no longer need a special spatial index.

The two best-known systems, with Geohash alongside for comparison:

| | **Geohash** | **S2** (Google) | **H3** (Uber) |
|---|---|---|---|
| Shape | Rectangle in lat/lon | "Square" on a cube face | Hexagon (+12 pentagons) on an icosahedron |
| Cell subdivision | 32 children | 4 children | 7 children |
| Index | Z-order | Hilbert | Hierarchical, packed into bits |
| Exact parent–child nesting | Yes (prefix) | **Yes** (ID range) | **Approximate** (children do not fit exactly) |
| Distortion near the poles | **Large** | Small (≈ 2× area) | Small (≈ 2× area) |

This page builds S2 **from scratch** in Python and checks it against the library, then shows what **spatial search in a sorted list** looks like, and finally looks at H3 through experiments.

## ⚙️ How S2 builds a cell ID

A point `(lat, lng)` becomes a 64-bit number in a few steps:

1. **Sphere → cube.** Convert `(lat, lng)` into a unit vector `(x, y, z)`. The cube **face** whose axis the vector is closest to is `face` (0…5).
2. **Coordinates on the face** `(u, v) ∈ [−1, 1]` by central (gnomonic) projection: divide the vector by its largest component.
3. **Quadratic transform** `u → s`, `v → t ∈ [0, 1]`. A grid directly on `(u,v)` makes the cells near the corners **much smaller** than at the centre. The quadratic formula corrects this and makes the cell areas nearly equal.
4. **Discretization** at level 30: `i = ⌊s · 2³⁰⌋`, `j = ⌊t · 2³⁰⌋`.
5. **Hilbert position.** Read the bits of `i` and `j` from top to bottom. At each level the pair `(iₖ, jₖ)` says which of the four sub-squares we are in, and the curve's **orientation** (whether `i` and `j` are swapped, whether they are inverted) determines this two-bit "digit" and updates the orientation for the next level. That gives 60 bits.
6. **Packing:** `ID = face(3 bits) | pos(60 bits) | 1`. The rightmost `2·(30 − level)` bits stay zero, and the trailing "1" **marks the level**: the position of the last "1" tells us which level we are at.

**Consequences** (all simple bit operations):

- **Level** = from the position of the last "1".
- **Parent** = clear the trailing bits and set a new "1".
- **Children** = 4 new "1" positions (two bits lower).
- **Descendant range** = `[ID − lsb + 1, ID + lsb − 1]`: a continuous range.

## 🐍 S2 from scratch in Python

```python title="s2cell.py" linenums="1"
import math

MAX_LEVEL = 30
SWAP, INVERT = 1, 2
POS_TO_IJ = ((0, 1, 3, 2), (0, 2, 3, 1), (3, 2, 0, 1), (3, 1, 0, 2))   # position -> (i<<1 | j), by orientation
POS_TO_ORIENT = (SWAP, 0, 0, INVERT | SWAP)


def latlng_to_xyz(lat, lng):
    phi, theta = math.radians(lat), math.radians(lng)
    return (math.cos(theta) * math.cos(phi), math.sin(theta) * math.cos(phi), math.sin(phi))


def xyz_to_face_uv(p):
    face = max(range(3), key=lambda k: abs(p[k]))
    if p[face] < 0:
        face += 3
    x, y, z = p
    u, v = {0: (y / x, z / x), 1: (-x / y, z / y), 2: (-x / z, -y / z),
            3: (z / x, y / x), 4: (z / y, -x / y), 5: (-y / z, -x / z)}[face]
    return face, u, v


def face_uv_to_xyz(face, u, v):
    return {0: (1, u, v), 1: (-u, 1, v), 2: (-u, -v, 1),
            3: (-1, -v, -u), 4: (v, -1, -u), 5: (v, u, -1)}[face]


def uv_to_st(u):                     # quadratic projection: cell areas become nearly equal
    return 0.5 * math.sqrt(1 + 3 * u) if u >= 0 else 1 - 0.5 * math.sqrt(1 - 3 * u)


def st_to_uv(s):
    return (4 * s * s - 1) / 3 if s >= 0.5 else (1 - 4 * (1 - s) ** 2) / 3


def face_ij_to_id(face, i, j):
    """Cell ID at level 30: 3 face bits + 60 bits of Hilbert position + 1 trailing bit."""
    orient = face & SWAP
    pos = 0
    for k in range(MAX_LEVEL - 1, -1, -1):
        ij = (((i >> k) & 1) << 1) | ((j >> k) & 1)
        digit = POS_TO_IJ[orient].index(ij)
        pos = (pos << 2) | digit
        orient ^= POS_TO_ORIENT[digit]
    return (face << 61) | (pos << 1) | 1


def latlng_to_cell(lat, lng, level=MAX_LEVEL):
    face, u, v = xyz_to_face_uv(latlng_to_xyz(lat, lng))
    n = 1 << MAX_LEVEL
    i = max(0, min(n - 1, int(uv_to_st(u) * n)))
    j = max(0, min(n - 1, int(uv_to_st(v) * n)))
    return parent(face_ij_to_id(face, i, j), level)


def lsb(cell):
    return cell & -cell


def level(cell):
    return MAX_LEVEL - ((lsb(cell).bit_length() - 1) >> 1)


def parent(cell, lvl):
    new = 1 << (2 * (MAX_LEVEL - lvl))
    return (cell & -new) | new


def children(cell):
    step = lsb(cell) >> 2
    return [cell - lsb(cell) + step * (2 * k + 1) for k in range(4)]


def range_min(cell):
    return cell - (lsb(cell) - 1)


def range_max(cell):
    return cell + (lsb(cell) - 1)


def cell_to_face_ij(cell):
    """(face, i, j, size): the cell's minimum corner in level-30 units, and its side length."""
    face = cell >> 61
    lvl = level(cell)
    orient = face & SWAP
    i = j = 0
    for k in range(lvl):
        digit = (cell >> (60 - 2 * k - 1)) & 3
        ij = POS_TO_IJ[orient][digit]
        i = (i << 1) | (ij >> 1)
        j = (j << 1) | (ij & 1)
        orient ^= POS_TO_ORIENT[digit]
    size = 1 << (MAX_LEVEL - lvl)
    return face, i * size, j * size, size


def cell_to_latlng(cell):
    """Cell centre."""
    face, i, j, size = cell_to_face_ij(cell)
    n = 1 << MAX_LEVEL
    return face_ij_point_to_latlng(face, (i + size / 2) / n, (j + size / 2) / n)


def face_ij_point_to_latlng(face, s, t):
    x, y, z = face_uv_to_xyz(face, st_to_uv(s), st_to_uv(t))
    return math.degrees(math.atan2(z, math.hypot(x, y))), math.degrees(math.atan2(y, x))


def cell_to_token(cell):
    return f'{cell:016x}'.rstrip('0') or '0'
```

### Usage

```python
from s2cell import *

c = latlng_to_cell(41.72, 44.80, 17)                         # Tbilisi, level 17
print('ID:      ', c)
print('token:   ', cell_to_token(c), ', level', level(c))
print('bits:    ', format(c, '064b'))
print('centre:  ', tuple(round(v, 5) for v in cell_to_latlng(c)))
p = parent(c, 10)
print('parent (10):', cell_to_token(p), '| children:', [cell_to_token(x) for x in children(p)])
leaf = latlng_to_cell(41.72, 44.80, 30)
print('leaf is in the cell range:', range_min(c) <= leaf <= range_max(c))
```

```text
ID:       4630840826652524544
token:    40440d3254 , level 17
bits:     0100000001000100000011010011001001010100000000000000000000000000
centre:   (41.72011, 44.80006)
parent (10): 40440d | children: ['40440c4', '40440cc', '40440d4', '40440dc']
leaf is in the cell range: True
```

Notice that **the parent's token (`40440d`) is not a prefix of every child** (`40440c4`). A token is the hexadecimal form of the ID without trailing zeros, and the "1" of the parent and of the child sit in different places. So working with ranges (`range_min`/`range_max`) is correct, and working with **string prefixes is not**.

!!! success "Verification"
    `s2cell.py` was compared with **s2sphere** (the Python port of S2) on 20,000 random points at random levels (0…30): ID, token, level, parent, the 4 children, `range_min`/`range_max` and the cell centre **match in every case**. The JavaScript version used in the demo gives the same IDs, tokens, ranges and children in 500 random checks.

## 🔍 Region search in a sorted list

This is why we need all of this. We **sort** the points' IDs (in a database this is an ordinary B-tree index). The question "what fell inside a 10 km circle?" is answered like this:

1. **Cover** the circle with cells: start with the 6 faces and for every cell either skip it (it is outside the circle), take it whole (it is inside), or split it into 4 children. The third case stops at the maximum level.
2. Each cell is **one continuous ID range**. Merge adjacent ranges.
3. For each range, use `bisect` to find the points in the sorted list.
4. Filter the candidates by exact distance, because the covering also contains extra area.

We compute a cell's "cap" (bounding circle) as the **maximum angle from the corners to the centre**. The cell is convex (its sides are great-circle arcs), so the point farthest from the centre is one of its vertices.

```python title="cover.py" linenums="1"
import bisect
import math
import random
from s2cell import *


def angle(a, b):
    """Central angle between two unit vectors (in radians)."""
    d = a[0] * b[0] + a[1] * b[1] + a[2] * b[2]
    return math.acos(max(-1.0, min(1.0, d)))


def unit(p):
    n = math.sqrt(sum(c * c for c in p))
    return tuple(c / n for c in p)


def cell_cap(cell):
    """The cell's bounding "cap": (centre as a unit vector, radius in radians)."""
    face, i, j, size = cell_to_face_ij(cell)
    n = 1 << MAX_LEVEL
    pt = lambda a, b: unit(face_uv_to_xyz(face, st_to_uv(a / n), st_to_uv(b / n)))
    center = pt(i + size / 2, j + size / 2)
    corners = [pt(i, j), pt(i + size, j), pt(i, j + size), pt(i + size, j + size)]
    return center, max(angle(center, c) for c in corners)


def cover_circle(lat, lng, radius_m, max_level):
    """Cells whose union fully covers the circle (it may contain extra area)."""
    c0 = latlng_to_xyz(lat, lng)
    r0 = radius_m / 6371008.8
    out, stack = [], [f << 61 | 1 << 60 for f in range(6)]      # 6 faces (level 0)
    while stack:
        cell = stack.pop()
        center, rad = cell_cap(cell)
        d = angle(c0, center)
        if d > r0 + rad:
            continue                                            # entirely outside
        if d + rad <= r0 or level(cell) == max_level:
            out.append(cell)                                    # entirely inside, or already the smallest
        else:
            stack.extend(children(cell))
    return sorted(out)


def merge_ranges(cells):
    """Merge the ID ranges of adjacent cells."""
    ranges = []
    for c in sorted(cells):
        lo, hi = range_min(c), range_max(c)
        if ranges and lo <= ranges[-1][1] + 2:
            ranges[-1][1] = max(ranges[-1][1], hi)
        else:
            ranges.append([lo, hi])
    return ranges
```

### Usage: 200,000 points, a 10 km circle

```python
import bisect
import math
import random
from cover import *

rnd = random.Random(8)


def hav(a, b):
    la1, lo1, la2, lo2 = map(math.radians, (*a, *b))
    x = math.sin((la2 - la1) / 2) ** 2 + math.cos(la1) * math.cos(la2) * math.sin((lo2 - lo1) / 2) ** 2
    return 2 * 6371008.8 * math.asin(math.sqrt(x))


pts = [(rnd.uniform(41.0, 43.6), rnd.uniform(40.0, 46.7)) for _ in range(200000)]
index = sorted((latlng_to_cell(la, lo), k) for k, (la, lo) in enumerate(pts))
keys = [c for c, _ in index]

q, R = (41.72, 44.80), 10000
for lvl in (8, 10, 12):
    cells = cover_circle(*q, R, lvl)
    ranges = merge_ranges(cells)
    cand = []
    for lo, hi in ranges:
        a, b = bisect.bisect_left(keys, lo), bisect.bisect_right(keys, hi)
        cand += [index[t][1] for t in range(a, b)]
    hits = [k for k in cand if hav(q, pts[k]) <= R]
    print(f'level {lvl:2}: cells {len(cells):2}, ranges {len(ranges):2}, candidates {len(cand):4}, answer {len(hits)}')

brute = [k for k, p in enumerate(pts) if hav(q, p) <= R]
print('brute-force search:', len(brute), ', matches:', sorted(hits) == sorted(brute))
```

```text
level  8: cells  4, ranges  2, candidates 5445, answer 378
level 10: cells 13, ranges  2, candidates 1105, answer 378
level 12: cells 81, ranges 12, candidates  543, answer 378
brute-force search: 378 , matches: True
```

At every level **the answer is the same and matches the brute-force search**; only the cost differs. A finer covering (a deeper level) means fewer **candidates** (5,445 → 543 out of 200,000) and more **ranges** (2 → 12), i.e. we check fewer points by exact distance but do more lookups in the list. This balance is exactly what databases need; usually 8–20 ranges work well.

## 🔷 H3: hexagons

H3 projects the Earth onto an **icosahedron** (20 triangular faces) and covers each face with hexagons. It has 16 resolutions (0…15). Each cell splits into **7** cells at the next resolution (**aperture 7**). A small limitation: at the 12 vertices of the icosahedron the cells are **pentagons** (a topological necessity on a sphere).

On this page we do not build H3 ourselves (it is far more complex: the icosahedron's 122 base cells, rotations and pentagon exceptions). We use the official `h3` library (4.5.0) and run experiments with it.

```python
import h3

cell = h3.latlng_to_cell(41.72, 44.80, 9)
print(cell, h3.get_resolution(cell), h3.cell_to_latlng(cell))
print('neighbours (ring 1):', len(h3.grid_ring(cell, 1)), ', disk k=2:', len(h3.grid_disk(cell, 2)))
print('parent (8):', h3.cell_to_parent(cell, 8), '| children (10):', len(h3.cell_to_children(cell, 10)))
print('grid distance:', h3.grid_distance(cell, h3.grid_ring(cell, 3)[0]))
```

## ⚖️ Comparison in tables

A few experiments on both systems (the code is in the exercises; area statistics were computed with s2sphere's `Cell.exact_area()` and with `h3.cell_area`):

| Property | S2 | H3 |
|---|---|---|
| Spread of cell area (max/min) | ≈ 2.06 (level 10, 3,000 random cells) | ≈ 1.98 (res. 5, 20,000 random cells) |
| Neighbours | 4 side + 4 diagonal | 6, all equivalent |
| Neighbour distances | In Tbilisi at level 17: 67–75 m (side), 112 m (diagonal) | In Tbilisi at res. 8: 899–945 m for all 6 |
| Do children cover the parent exactly? | **Yes** (exactly 4) | **No**, the 7 children cover 92.9% of the parent's area |
| Growth per level | ×4 | ×7 |

**Conclusion.** S2 is ideal for **database indexing and range search** (a clear hierarchy, continuous ranges), while H3 is for **analysis**: the distance between cells is uniform, so a "k-ring" is a natural neighbourhood, which is convenient for aggregation and visualization.

    Run the search above with `max_level = 6, 8, 10, 12, 14`. How do the numbers of ranges and candidates change? Which level would you choose?

    ??? success "Solution"
        The loop is the same, only `for lvl in (6, 8, 10, 12, 14)`:

        ```text
        level  6: cells  3, ranges  1, candidates 48081, answer 378
        level  8: cells  4, ranges  2, candidates 5445, answer 378
        level 10: cells 13, ranges  2, candidates 1105, answer 378
        level 12: cells 81, ranges 12, candidates  543, answer 378
        level 14: cells 379, ranges 41, candidates  413, answer 378
        ```
        The answer is always the same (378), but the cost changes: every two levels the candidates drop noticeably (48,081 → 413), while the ranges grow (1 → 41). At levels 12–14 the candidates already approach the answer (543 and 413 vs 378), but at level 14 we need 41 separate lookups. The concrete choice **depends on the database**: a range query is cheap, an exact geometric check is expensive. Many systems cap the number of cells (e.g. 8–20 cells) and choose the level accordingly.

!!! question "Exercise 3: do they nest exactly?"
    Take an H3 cell at resolutions 5, 7 and 9 (in Tbilisi), merge the polygons of its 7 children (`shapely`) and compute: what fraction of the parent is covered by the children, and what fraction of the children's area lies outside the parent (a flat approximation in lat/lon, which is enough for small cells). Compare with S2.

    ??? success "Solution"
        ```python
        import h3
        from shapely.geometry import Polygon
        from shapely.ops import unary_union


        def poly(c):
            return Polygon([(lng, lat) for lat, lng in h3.cell_to_boundary(c)])


        for r in (5, 7, 9):
            p = h3.latlng_to_cell(41.72, 44.80, r)
            P = poly(p)
            ch = unary_union([poly(c) for c in h3.cell_to_children(p, r + 1)])
            print(r, len(h3.cell_to_children(p, r + 1)), round(P.intersection(ch).area / P.area, 3), round(ch.difference(P).area / ch.area, 3))
        ```
        ```text
        5 7 0.929 0.071
        7 7 0.929 0.071
        9 7 0.929 0.071
        ```
        The 7 children cover **92.9%** of the parent, and **7.1%** of the children's area lies outside the parent. This is the same at every resolution because the geometric picture is scale-invariant. In S2 the children cover the parent **exactly** (four sub-squares), so range search is correct. In H3 `cell_to_children` still exists by definition, but the "nested" cells do **not** give an exact geometric covering: a query on the parent's region cannot be turned exactly into a query on its children.
